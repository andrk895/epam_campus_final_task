## Nits (non-blocking)
- `get_settings()` is lazy, so the "fails at startup" behaviour only holds once something calls it at startup. In T0.3, `create_app()` (or a lifespan hook) should call `get_settings()` eagerly. Otherwise a missing `JWT_SECRET` would only show up on the first request that needs settings.
- `.env.example` ships `JWT_SECRET=change-me`, and that value is accepted. A minimum length (for example 32 characters for HS256) would stop weak secrets from being used. This is not required by the task.
- The `DATABASE_URL` default and the HS-only `JWT_ALGORITHM` Literal are deliberate, documented choices. They are consistent with D4 and the local-Postgres environment.

## Summary
T0.2 is fully implemented, and it stays within the task's scope. `Settings` is a frozen, typed pydantic-settings model covering every variable the task lists, with defaults that match the design decisions. A missing or blank `JWT_SECRET` produces a clear per-variable `ConfigurationError` that does not leak secret values. Settings are cached, can be injected through `SettingsDep`, and can be overridden with `dependency_overrides` or reset with `cache_clear()`. The tests check these behaviours directly, including the error cases, and are isolated from the host environment. Lint, format, type checks and tests all pass.
