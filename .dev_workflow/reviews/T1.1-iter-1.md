- [x] SQLAlchemy 2.x engine + session factory: met. `src/app/db/session.py` has `create_db_engine(settings)` (`pool_pre_ping=True`, lazy connect) and `create_session_factory(engine)` (`autoflush=False`, `expire_on_commit=False`). SQLAlchemy 2.1.4 and psycopg 3.3.6 are installed.
- [x] `get_db` dependency yields one session per request: met. `get_db(request)` uses `app.state.session_factory` and yields inside `with session_factory() as session`. `DbSessionDep` is exported.
- [x] The app can connect to a local PostgreSQL instance: met. `app.main.app` (built from `.env`) ran `SELECT current_database()` and got `pm_app`. The tests get `pm_test`.
- [x] The session is closed after each request: met. Checked with the programmer's tests and with my own probe, covering success, `HTTPException`, uncaught `RuntimeError` and concurrent requests. Every case ended with `checkedout() == 0`.

## Issues (blocking)
None.

## Nits (non-blocking)
- `tests/test_db.py:129-136` (`test_create_app_builds_engine_from_settings`): `engine.dispose()` doesn't run if an assertion fails first. This has no practical effect because no connection is ever opened.
- The DB tests need a running PostgreSQL and fail rather than skip when it is unreachable. That is fine for this environment; T1.4 fixtures can centralise `TEST_DATABASE_URL` / `make_settings` (already recorded as carry-over).
- `get_db` catches `BaseException`, so a `GeneratorExit` also triggers a rollback. This is harmless, but `Exception` would be enough because `close()` already rolls back.

## Summary
The engine, session factory and per-request `get_db` follow the spec's layout (`src/app/db/`) and work against the local PostgreSQL. Sessions are closed after every request, including failed and concurrent ones. A failed request rolls back its transaction, and the engine is disposed on shutdown. The startup and `/health` behaviour from Phase 0 is unchanged. Tests, ruff and mypy are clean, and nothing outside the task's scope was added.

VERDICT: APPROVED
