## Done-when criteria
- [x] Unit tests cover a valid token: `test_valid_token_round_trips`, `test_token_claims_are_sub_iat_exp_and_header_uses_configured_algorithm` (exact claim set and `alg` header checked), and an all-algorithms round trip.
- [x] Expired token, using a short expiry and a back-dated issue time: `test_expired_token_is_rejected` (issued 61 min ago, 60 min expiry) and `test_short_expiry_token_is_rejected_once_expired` (1 min expiry). These use the explicit `now=` argument, which is deterministic and needs no time-freezing library.
- [x] Tampered token: changed payload with the original signature, a flipped signature byte, a different secret, a different HS algorithm, and `alg: none` (made by PyJWT and by hand). All are rejected with the expected message.
- [x] Password verification: correct, wrong, empty and case-changed passwords; salted (unique) hashes; unicode; invalid stored hashes return False; argon2id prefix; the plain password does not appear in the hash.
- [x] Task bullets: `hash_password` and `verify_password` exist. `create_access_token(user_id, settings)` sets `exp = iat + JWT_EXPIRE_MINUTES` (60 by default, which is the required 1 hour) and `iat`. `decode_token` rejects expired, malformed and wrongly signed tokens. This matches D3 (argon2 via pwdlib) and D4 (PyJWT, HS256, `sub` = user id, 1 h).

## Nits (non-blocking)
- `src/app/core/security.py:20`: importing `argon2.exceptions` directly relies on a transitive dependency. It is pinned through `pwdlib[argon2]`, so this is acceptable. Listing `argon2-cffi` explicitly would make the dependency visible.
- Over-engineering check: `password_needs_rehash`, the `MAX_USER_ID` upper bound, the strict canonical-`sub` regex, the integer-only `iat`/`exp` check and the overflow guard all go beyond what the task asks. Each is small, fully tested and makes the API safer, with no extra dependencies, so they are acceptable. `password_needs_rehash` has no caller yet; T2.3 may use it or leave it.
- `Settings.jwt_secret` has no minimum length, so short secrets only trigger PyJWT's `InsecureKeyLengthWarning`. A minimum length (for example ≥ 32 bytes) could be enforced in config later, outside this task.
- For T2.3: run a dummy `verify_password` against a fixed hash when the login is unknown, so response timing does not reveal which logins exist (the programmer noted this too).

## Summary
The implementation is clean and has no FastAPI imports. It follows D3/D4. `decode_token` pins the configured algorithm, so `alg: none` and algorithm substitution are blocked, and it requires `exp`/`iat`/`sub`. It validates claim types strictly and turns every failure into one `InvalidTokenError` that keeps the PyJWT error as its cause, which suits the T2.4 dependency well. Every Done-when scenario is covered by meaningful tests, along with many extra error paths. Tests, ruff, ruff format and mypy all pass. The only failing test in the suite is the known out-of-scope `test_db.py` problem. The extra safety measures are not excessive for a security module.
